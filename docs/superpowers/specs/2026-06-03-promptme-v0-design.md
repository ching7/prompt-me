## 1. 一句话定义

PromptMe 不是日历软件，而是一个基于福格行为模型（B=MAP）的个人行为操作系统：
把用户**已有的规划**（飞书任务文档 + 苹果日历）拉到手机上，在用户**卡壳的那一秒**用 AI 介入，
通过提示（Prompt）、降低门槛（Ability）、即时反馈（Motivation），把目标变成持续行动。

Slogan：**记录每一次行动，成为想成为的人。 / Prompt Yourself Into Action.**

---

## 2. 目标与北极星

作者做这个项目有三个动机，但它们对「怎么做」的要求互相冲突：

| 目标 | 真正要求 | 风险 |
|---|---|---|
| A. 体验 AI code / vibe coding | 任何有复杂度的项目都满足 | 约束力近乎为零，是副产品 |
| B. 丰富 GitHub / 为跳槽 | 一个完成度高、有人真用、文档好的项目 | 半成品 mega-app 是减分项 |
| C. 管理自己的行为（**重点**） | 必须跑在自己设备上、可靠、能降低执行阻力 | 自己都不用 → A、B 同时归零 |

**北极星 = C。** 围绕 C 设计，A 和 B 会自动达成。
MVP 唯一验收标准：**「作者明天早上会不会主动打开它。」**

补充约束（来自作者确认）：
- 跳槽方向「暂不为展示技术，只求快」 → 技术选型一律选最快上手、最少运维的。
- V0 节奏「分阶段，先上可用核心」 → 不把最难的集成压在第一波。

## 3. 产品模型：规划与跟踪分离

作者的真实工作流（来自其飞书文档与苹果日历截图）：

- **飞书文档** = 晨间**任务**规划，结构为「日期 → 艾森豪威尔四象限（重要紧急 / 重要非紧急 / 不重要紧急 / 不重要不紧急）→ 嵌套 checkbox」。
- **苹果日历** = **时间块**排程，分「工作 / 成长 / 生活 / 最重要」几条日历。

由此确立模型——**绝不让用户在 PromptMe 里重录（双重录入是头号弃用杀手）**：

> **Mac 早晨 = 规划**：继续用飞书 + 苹果日历，习惯完全不动。
> **手机（安卓）= 提示 + 跟踪**：PromptMe 把两边拉过来，合成「今日」，提示、让用户打卡跟进。

P（提示）是核心，所以**安卓优先**，Mac 端留到 V1。
产品原生采用**四象限**作为优先级模型（贴合作者既有思考方式，「重要紧急」自动置顶为今日聚焦）。

## 4. 福格行为模型映射（B = M·A·P）

| 模型要素 | 在 PromptMe 中的落地 |
|---|---|
| **P** Prompt（提示） | 定时本地通知 + 常驻『今日·重要紧急』通知（显示在锁屏）；福格式低门槛文案 |
| **A** Ability（能力/门槛） | 任务拆解；[太难了] 触发「无底线降级」到 2 分钟微习惯 |
| **M** Motivation（动机） | [我做到了] 即时庆祝动画；连续天数 / 完成率反馈 |
| **B** Behavior 调试 | AI「复盘未完成」：定位 M/A/P 哪一项塌了并给出具体修法 |

三个失败原因天然对应 M/A/P，而当场最可靠的解都一样——**缩到 2 分钟 + 把新提示重打到锁屏**：

| 失败原因 | 塌的是 | 现场解 |
|---|---|---|
| 忘记 | P 提示 | 缩小 + 重新提示（动机推不动、累也无法立刻消除，但「变小」永远做得到） |
| 太累 | A 能力/精力 | 同上 |
| 没动力 | M 动机 | 同上 |

## 5. V0 范围：分两波交付

两波共用同一套「结构化任务文本 → Task」解析器，无废弃代码（仅切换数据源）。

### 🟢 第一波（约 4 周，纯 Dart，无后端，立刻能每天用）

1. **苹果日历订阅**（只读、定时刷新）
   - 苹果「公开日历」生成的 webcal / 已发布 ICS 链接（如 `https://p209-caldav.icloud.com.cn/published/...`）。
   - 机制：HTTP GET → 解析 VEVENT → 定时刷新。无认证、无 CalDAV 协议、零数据风险。
   - 需把要拉的每条日历分别「公开」拿到订阅链接。
2. **飞书任务「粘贴 Markdown」导入**（临时入口）
   - 作者把飞书文档导出/复制为 Markdown → 粘进 app → 解析「日期标题 + 四象限标签 + checkbox（含嵌套）」成 Task。
   - 该解析器第二波原样复用，仅换数据源（粘贴 → API），非废弃代码。
3. **四象限今日时间线**（主视图，见 §7）
4. **福格闭环**：打卡 / 连续天数 / 完成率
5. **通知**：定时提示 + 常驻『今日·重要紧急』
6. **AI 整理今日**（优先级划分/建议，见 §6）
7. **AI 复盘未完成**（原因分析，见 §6）
8. **[我做到了] / [太难了] 即时降级闭环**（特色交互，见 §8）

AI 在第一波用 **BYO-key（自带 key，存本机）直连**，安卓原生无 CORS 限制，不必等后端。

### 🔵 第二波（约 +2–3 周，接轻量后端）

- **轻量 Serverless 函数**（默认 Cloudflare Workers / Vercel；第二波时若作者更顺手也可用 Spring Boot 写这个极小代理——技术选型不影响架构）。
- **飞书 OAuth 链接自动同步**：把「粘贴」升级为「贴链接自动拉」，解析器不变，彻底消灭手动。
- 可选：把 AI key 挪到后端代理后面（单人用非必须；改动仅为请求地址）。

后端职责极小：飞书 OAuth token 交换 + 刷新 + docx 读取代理。App 数据全程存本地。

## 6. AI 功能（按需、批量、建议性；≈ 每天 2 次调用，成本极低）

设计原则：AI 是参谋不是独裁，用户点「采纳」才生效；结构化 JSON 输出便于渲染成可点动作；数据不足时优雅提示而非硬分析。

### 6.1 任务优先级划分 / 建议 —— 一键「整理今日」
- 触发：早晨任务进来后手动点一下。
- 输入：今日任务 + 今日日历占用（时间余量）。
- 输出：给未分类任务**建议四象限** + 推荐**今日聚焦 3 件** + 每条一句理由。
- 价值：降低「今天先干啥」的决策摩擦（A + P）。第一天即可用。

### 6.2 未完成 / 过期任务原因分析 —— 「复盘未完成」
- 触发：傍晚或在「过期」列表手动点一下。
- 输入信号：用户亲手打标的失败原因（来自 [太难了]）、被推迟次数（`rolloverCount`）、所属象限（总被推的「重要非紧急」= 拖延信号）、预估耗时（是否太大）、当天日历是否排满。
- 输出：可能原因（M/A/P 哪个塌）+ 一个具体调整（拆小 / 改时间 / 降门槛），可一键应用。
- 注意：需积累约一周数据才有料；因有 [太难了] 的标注，分析不靠猜。

### 6.3 Provider
- 默认走一个 provider（建议 Claude Sonnet，够用且便宜），做成**可切换**（Claude / OpenAI / DeepSeek / Qwen / Gemini，作者有哪家 key 用哪家）。

## 8. 特色交互：[我做到了] / [太难了]

位置：今日时间线每个任务上（以及点通知打开 App 后）。

- **[我做到了]**：标记完成 → 庆祝动画（confetti / lottie）→ 连续天数 +1 小动效。强化 M。
- **[太难了]**：
  1. 快速勾选原因：忘记 / 太累 / 没动力（记进 `TaskEvent` 日志）。
  2. 后台调 AI：当前任务 + 原因 → 生成**无底线降级**的 2 分钟微版本
     （例：「写郑州银行进度报告」+ 太累 →「只打开文档，写一句话」）。
  3. 将微版本作为新的**『2 分钟微习惯』提示刷到锁屏**（沿用通知服务）。
  4. 再点 [太难了] 就在当前微版本基础上**继续往下降**（「打开文档」→「只看一眼标题」），真·无底线。

可选升级（不进 V0）：把两个按钮做成**通知的操作按钮**（不开 App 就能响应）——需后台跑 AI（background isolate），复杂度上来，留作锦上添花。

## 9. 数据模型（本地 SQLite / Drift）

- **Project**：`id, title, notes, createdAt`
- **Task**：`id, projectId?, parentTaskId?(嵌套), title, quadrant(四象限枚举), source(manual/feishu), scheduledDate?, estMinutes?, status, completedAt, rolloverCount(被推迟次数), firstScheduledDate?, currentPromptText(锁屏显示文案，降级后更新), downgradeLevel`
- **TaskEvent**（行为日志）：`id, taskId, type(done/too_hard), reason?(忘记/太累/没动力), microVersionText?, createdAt`
- **CalendarEvent**（订阅来，只读）：`id, subscriptionId, uid, title, start, end, allDay, calendarName`
- **Subscription**（日历订阅源）：`id, url, displayName, lastFetchedAt`

派生数据：连续天数 / 完成率由 `Task.completedAt` 与 `TaskEvent` 聚合算出，不另存。

四象限枚举：`重要紧急 / 重要非紧急 / 不重要紧急 / 不重要不紧急`。

## 10. 模块边界（各自单一职责、可独立测试）

- **数据层**：Drift DAO。
- **福格闭环域**：四象限优先级、今日聚焦、打卡、连续天数/完成率计算（纯逻辑，易测）。
- **日历订阅服务**：GET .ics → 解析 VEVENT → 定时刷新。
- **任务解析服务**：Markdown / 飞书 block → Task（两波共用）。
- **AI 服务**：组装 prompt → 调 provider → 解析结构化 JSON → 渲染成可点建议/动作。第一波直连（BYO key），第二波可挪到后端代理。
- **通知服务**：定时提示 + 常驻『今日·重要紧急』+ 微习惯刷新。
- **UI**：今日时间线 / 项目列表 / 设置（订阅链接、AI key/provider、飞书授权-第二波）。

## 11. 技术栈（V0）

| 关注点 | 选型 | 理由 |
|---|---|---|
| 客户端框架 | **Flutter（安卓优先）** | 一套代码，后续可出 macOS/Web；原生通知是 P 的关键，PWA 做不好 |
| 本地数据库 | **Drift（SQLite）** | 数据是关系型（项目→任务、事件、日志、聚合查询），SQL 比 Hive/Isar 顺手 |
| 状态管理 | **Riverpod** | 社区主流、AI 写起来稳 |
| 通知 | **flutter_local_notifications** | 定时 + 常驻，纯客户端无需服务器 |
| 网络 + 解析 | **http + iCalendar 解析包** | 订阅源 = GET + 解析 VEVENT |
| 动画 | **confetti / lottie** | 庆祝动画 |
| 后端（第二波） | **轻量 Serverless**（默认） | 只是飞书 token 代理 + docx 读取，代码与运维最少 |

## 12. 错误处理与测试

- **网络/订阅失败**：显示上次成功数据 + 错误提示，不崩。
- **解析容错**（.ics、飞书 Markdown）：跳过坏行，不整体失败。
- **AI 失败/超时**：明确提示并允许重试；[太难了] 的降级在 AI 不可用时回退到本地规则（如机械截断为「先做 2 分钟」）。
- **飞书 token 过期**（第二波）：静默刷新；刷新失败引导重新授权。
- **测试**：解析器（ics + 飞书 markdown）、福格聚合（连续天数/完成率）做纯函数单元测试；DAO 做集成测试；TDD 友好。

## 15. 实现期需核实的事项

1. **飞书 OAuth（第二波）**：确认 app_secret 换 token 必须服务端、所需权限 scope（如 `docx:document:readonly` / 云文档只读）、自建应用 vs 应用商店应用、回调 URI 配置。
2. **苹果公开日历订阅**：每条日历需单独「公开」；确认 GET 已发布 URL 直接返回 iCalendar 文本。
3. **Flutter Web CORS（V1）**：iCloud 订阅源在浏览器端可能被 CORS 拦，需小代理；安卓原生不受影响。
4. **AI 客户端直连（BYO key）**：确认各 provider 允许从安卓原生客户端直连（OpenAI/Anthropic/DeepSeek/Qwen/Gemini）。
5. **通知操作按钮（可选升级）**：[做到了]/[太难了] 做成通知按钮需 background isolate 执行 AI。
