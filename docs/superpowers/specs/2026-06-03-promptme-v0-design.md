# PromptMe V0 设计文档

- 日期：2026-06-03
- 阶段：V0（第一个可独立交付的子项目）
- 目标平台：Flutter / Android（优先），纯 Dart、纯本地，不联网账号、不接 AI

---

## 1. 背景与目标

PromptMe 是一个基于福格行为模型（B=MAP，行为 = 动机 × 能力 × 提示）的个人行为管理工具。它**不是**第三个让用户重新录入任务的地方，而是补齐用户现有工作流缺失的那一层：**主动提示（P）+ 反馈/复盘（M）**。

作者本人的真实工作流是：
1. 每天早上在**飞书文档**里规划当天任务，按**艾森豪威尔四象限**组织，任务可勾选、可嵌套子任务。
2. 在**苹果日历**里做时间安排（多个分类日历：工作/成长/生活/最重要）。

这两个工具各自的盲区：飞书文档不会主动提醒、不做反馈复盘；苹果日历只在事件点提醒、也不做反馈复盘。

V0 的唯一验收标准：**作者本人第二天早上会主动打开它来规划当天。** 如果做不到这一点，后续所有功能都无意义。

### 决策记录（为什么是这个形态）
- **为什么 Flutter 安卓优先**：P（提示）是福格模型里最能撬动行为的杠杆，而安卓上「可靠、可定时、可常驻」的通知必须用原生能力，PWA 做不好。Flutter 同套代码后续还能出 macOS/Web（V1）。
- **为什么 PromptMe 接管每日规划（而非只读拉取飞书）**：飞书文档读取需要开放平台 OAuth + 文档块解析，做不进 V0 的纯 Dart 范围；且作者确认该文档为纯个人规划，可整体迁入。任务模型直接复刻飞书的「每天 × 四象限 × 嵌套勾选」，使迁移零认知成本。
- **为什么苹果日历用订阅而非 CalDAV**：苹果「公开日历」生成的 `https://p###-caldav.icloud.com.cn/published/...` 链接是**静态 .ics 订阅源（webcal）**，HTTP GET 即得，无认证、无 PROPFIND/ETag，避开了 CalDAV 协议的全部痛点，且只读、零数据风险。

## 2. 产品定位（一句话）

> 左手是「每日艾森豪威尔任务清单」（复刻飞书规划体验），右手是「订阅进来的苹果日历时间块」，福格的**提示**与**反馈**层把两者串成一条「今日时间线」。

**关键衔接点**：福格的「今日 3 件事」= 艾森豪威尔「重要」象限（重要紧急 + 重要非紧急）的头部。四象限本身替用户筛好了「什么最重要」，PromptMe 把它抓出来做成提示。

## 3. 范围

### V0 做（IN）
- **每日任务规划**：按天 × 四象限（重要紧急 / 重要非紧急 / 不重要紧急 / 不重要不紧急）× 可勾选任务 + 嵌套子任务；完成显示划线。
- **今日 3 件事（福格 P）**：自动从「重要」象限头部取，做成**常驻通知**（Android ongoing notification）+ **定时本地提示**，措辞走福格式低门槛风格（例：「现在只要推进 3 分钟：……」）。
- **苹果日历订阅**：订阅 webcal/已发布 ICS 链接，只读、定时自动刷新；顺带支持本地 `.ics` 文件导入（解析代码同源）。
- **今日时间线**：把「订阅来的时间块」+「今日重要任务」+「已完成项」合并到一个视图。
- **反馈（M，非 AI 版）**：今日完成率 + 连续打卡天数。
- **本地存储**：SQLite（Drift），无账号、无网络同步。

### V0 不做（OUT）
- AI（任务拆解、日报）——V1
- macOS/Web 端——V1
- 真·CalDAV 客户端、飞书集成、屏幕使用时间、真·锁屏/桌面 Widget——V2
- CalDAV 双向写回——V3
- 周报/月报、多用户账号、跨端同步后端

### 后续路线图（仅作上下文，不在本 spec 详细设计）
- **V1**：AI 任务拆解 + AI 日报；Flutter 出 macOS/Web 覆盖 Mac（处理浏览器 CORS，可能加一行代理拉取订阅源）。
- **V2**：真·CalDAV 客户端（主攻飞书带密码认证）；屏幕使用时间（Kotlin 平台通道）；真·锁屏/桌面 Widget（home_widget）；如需，跨端同步后端。
- **V3**：CalDAV 双向写回（限定「新建/标记完成」范围，做好数据安全，永不碰重复规则）。

## 4. 架构与模块边界

每个模块职责单一、通过明确接口通信、可独立测试。

```
┌─────────────────────────────────────────────┐
│ UI 层（Flutter widgets, Riverpod 消费）          │
│  · 今日页(TodayScreen)  · 规划页(PlanScreen)     │
│  · 设置页(SettingsScreen)                       │
└───────────────┬─────────────────────────────┘
                │ 读 ViewModel / 发命令
┌───────────────▼─────────────────────────────┐
│ 状态层（Riverpod providers）                     │
└───────────────┬─────────────────────────────┘
                │
┌───────────────▼─────────────────────────────┐
│ 服务/领域层                                       │
│  · TaskService        （任务 CRUD、今日3件事、     │
│                         完成率、连续天数、结转）    │
│  · CalendarSyncService（拉取/解析/去重/定时刷新）   │
│  · NotificationService（定时提示 + 常驻今日3件事）  │
└───────────────┬─────────────────────────────┘
                │
┌───────────────▼─────────────────────────────┐
│ 数据层（Drift / SQLite）                          │
│  · tasks  · calendar_subscriptions             │
│  · calendar_events                             │
└─────────────────────────────────────────────┘
        外部：HTTP GET 订阅源(.ics) → 解析
        系统：flutter_local_notifications
```

每个模块的「做什么 / 怎么用 / 依赖什么」：
- **TaskService**：管理艾森豪威尔任务树与统计。依赖数据层。不知道 UI、不知道日历。
- **CalendarSyncService**：把订阅 URL 变成本地缓存的 `calendar_events`。依赖 http + ics 解析 + 数据层。不知道任务、不知道 UI。
- **NotificationService**：把「今日 3 件事」与提示时间变成系统通知。依赖 flutter_local_notifications + TaskService 的查询结果。
- **数据层**：纯持久化，无业务逻辑。

## 6. 关键数据流

1. **早晨规划**：用户打开「规划页」→ 在四象限中增删任务、加嵌套子任务、排序 →（可选）点「把昨天未完成的『重要』任务拉到今天」。
2. **派生今日 3 件事**：TaskService 从今天 quadrant∈{重要紧急, 重要非紧急} 的顶层未完成任务按 sort_order 取前 3 → NotificationService 更新常驻通知 + 安排定时提示。
3. **日历刷新**：App 启动时 + 定时（如每 30 分钟/可配）触发 CalendarSyncService → 对每个 enabled 订阅 HTTP GET → 解析 VEVENT（仅展开当前可见窗口内的 RRULE）→ 按 uid upsert 进 `calendar_events`。
4. **今日时间线渲染**：今日页合并展示「今天的 calendar_events（时间块）」+「今天的重要任务」+「已完成项」，顶部显示完成率/连续天数。
5. **打卡**：用户勾选任务 → 写 `done/completed_at` → 完成率/连续天数刷新 → 常驻通知内容更新。

## 7. 提示（P）设计

- **常驻通知**：一条 ongoing notification 常驻通知栏/锁屏，显示「今日 3 件事」及完成进度（如 `1/3 已完成`）。这是原方案「锁屏卡片」的零原生成本实现。
- **定时提示**：用户可设若干提示时间（如早 9:00 规划提醒、晚 21:00 收尾提醒）。用 `flutter_local_notifications` 的定时调度，纯客户端，无需服务器。
- **福格式措辞**：提示文案强调低门槛，例：「现在只要推进 3 分钟：<重要任务标题>」，而非「该做某事了」。
- **权限降级**：若用户拒绝通知权限，退化为仅 App 内提醒，并引导去系统设置开启。

---

## 8. 日历订阅设计

- **来源**：苹果「公开日历」发布链接（`/published/`，静态 .ics）。形态为 `webcal://` 或 `https://`，统一按 https GET。
- **解析**：用 Dart 的 iCalendar 解析库读取 VEVENT；DTSTART 带 TZID 时按时区转换，统一以 UTC 存、本地时区显示。
- **刷新**：定时 + 启动时；失败时保留上次缓存事件，记录 `last_error`，UI 给出不打断的提示，下次周期重试。
- **去重**：按 `(subscription_id, uid, start)` upsert，避免重复刷新产生重复事件。
- **RRULE**：V0 仅展开「当前可见窗口」（如今天 ± 7 天）内的重复实例，够时间线用即可；EXDATE、复杂重复规则列为已知限制，留待后续。
- **本地 .ics 导入**：复用同一解析路径，作为附带能力。

---

## 9. 错误处理

- **网络/URL 错误**：捕获，写 `last_error`，继续展示缓存，绝不崩溃。
- **ICS 解析错误**：跳过畸形 VEVENT，记日志，继续解析其余。
- **通知权限被拒**：降级为 App 内提醒。
- **时区**：作为重点测试区域；解析时显式处理 TZID 与全天事件。
- **空数据**：今日页/规划页在无任务、无订阅时给出引导式空状态，而非空白。

## 10. 测试策略

- **单元测试（核心）**：
  - TaskService：今日 3 件事派生、完成率计算、连续天数计算、跨天结转。
  - ICS 解析：用固定 `.ics` fixture（含全天事件、带 TZID 事件、简单 RRULE）验证解析与时区。
  - 事件 upsert/去重（同一 uid 多次刷新不产生重复）。
- **Widget 测试**：今日页合并渲染；规划页四象限勾选与嵌套展示。
- **手动验收**：用作者本人真实的苹果「公开日历」链接跑通端到端订阅与展示。

## 11. 技术栈

| 关注点 | 选型 | 理由 |
|---|---|---|
| 框架 | Flutter（Android 优先） | 一套 Dart 后续可扩 macOS/Web |
| 本地数据库 | Drift（SQLite） | 关系型数据（任务树、事件、统计）用 SQL 最顺手 |
| 状态管理 | Riverpod | 社区主流、AI 协作稳定 |
| 通知 | flutter_local_notifications | 定时 + 常驻，纯客户端 |
| 网络 + 解析 | http + iCalendar 解析库 | 订阅即 GET + 解析 VEVENT |

组件均可替换，不构成架构锁定。

## 12. 待确认的设计决策（评审时可推翻）

1. **子任务嵌套**：支持树状嵌套，UI 实际展示 2–3 层。是否够用？
2. **跨天结转**：不自动滚动，提供「把昨天未完成的『重要』任务拉到今天」动作。是否符合你的习惯？
3. **今日 3 件事来源**：取「重要紧急 + 重要非紧急」头部 3 个。固定 3 个，还是允许配置数量？
4. **提示时间**：默认提供「早晨规划提醒 + 晚间收尾提醒」两个，可增删。默认时间设多少？
5. **RRULE 范围**：V0 只展开可见窗口内的重复事件，复杂重复留为已知限制。可接受？
